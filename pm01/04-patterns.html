4Паттерны проектирования

Паттерн проектирования — это типовое решение типовой задачи. Не кусок кода, а идея, которую можно применить в разных проектах. Паттерны не изобретают — их обнаруживают в успешных проектах.

Откуда взялись паттерны
В 1994 году четыре автора (Эрих Гамма, Ричард Хелм, Ральф Джонсон, Джон Влиссидес) выпустили книгу «Design Patterns» — в ней описали 23 классических паттерна. Их называют «банда четырёх» (Gang of Four, GoF).

4.1. Три категории паттернов

КатегорияОтвечает заПримеры
Порождающие (Creational)Создание объектовSingleton, Factory Method, Builder, Prototype
Структурные (Structural)Композиция классов и объектовAdapter, Decorator, Facade, Proxy, Composite
Поведенческие (Behavioral)Взаимодействие между объектамиObserver, Strategy, Command, State, Iterator

4.2. Порождающие паттерны

Singleton (Одиночка)

Гарантирует, что у класса есть единственный экземпляр, и предоставляет к нему глобальную точку доступа.

public class Config {
    private static Config _instance;
    private Config() { }  // приватный конструктор
    public static Config Instance => _instance ??= new Config();
    public string DbConnection { get; set; }
}

// Использование:
Config.Instance.DbConnection = "...";
Классическая реализация на C# через свойство.

Когда использовать: конфигурация приложения, логгер, кэш, подключение к БД.
Осторожно: Singleton мешает тестированию (глобальное состояние). В современном коде часто заменяется на Dependency Injection.

Factory Method (Фабричный метод)

Определяет интерфейс для создания объекта, но позволяет подклассам решать, какой класс создавать.

interface ILogger { void Log(string msg); }

class FileLogger : ILogger { public void Log(string msg) { /* в файл */ } }
class ConsoleLogger : ILogger { public void Log(string msg) { /* в консоль */ } }

class LoggerFactory {
    public static ILogger Create(string type) => type switch {
        "file"    => new FileLogger(),
        "console" => new ConsoleLogger(),
        _         => throw new ArgumentException()
    };
}

var logger = LoggerFactory.Create("file");

Builder (Строитель)

Пошаговое создание сложного объекта. Позволяет строить объект с разными конфигурациями, не создавая конструктор с 20 параметрами.

var pizza = new PizzaBuilder()
    .WithSize("Large")
    .WithCheese()
    .WithPepperoni()
    .WithMushrooms()
    .Build();
Читается как естественный язык. Идеально для сложных объектов.

Prototype (Прототип)

Создание нового объекта через клонирование существующего. Полезно, когда создание «с нуля» дорого.

4.3. Структурные паттерны

Adapter (Адаптер)

Позволяет объектам с несовместимыми интерфейсами работать вместе. Как переходник для розетки.

Adapter превращает старый интерфейс в новый, ожидаемый приложением.

Decorator (Декоратор)

Добавляет объекту новую функциональность, оборачивая его. Можно накладывать «слоями».

IBeverage coffee = new Espresso();
coffee = new MilkDecorator(coffee);      // + молоко
coffee = new SugarDecorator(coffee);     // + сахар
coffee = new CreamDecorator(coffee);     // + сливки
Console.WriteLine(coffee.Cost());        // сумма всех добавок

Facade (Фасад)

Предоставляет простой интерфейс к сложной подсистеме. Пользователь не знает про 20 классов внутри — работает с одним.

Proxy (Заместитель)

Подменяет реальный объект, контролируя доступ к нему. Используется для ленивой загрузки, кэширования, проверки прав.

Composite (Компоновщик)

Позволяет работать с деревом объектов как с одним объектом. Пример — файловая система: папка и файл обрабатываются одинаково.

4.4. Поведенческие паттерны

Observer (Наблюдатель)

Один объект (Subject) уведомляет других (Observers) об изменениях своего состояния. Основа event-driven систем.

Subject при изменении уведомляет всех подписчиков через notify().

Где применять: события в UI, модель MVC/MVVM, подписки, новостные каналы, реактивное программирование.

Strategy (Стратегия)

Определяет семейство взаимозаменяемых алгоритмов. Позволяет менять поведение объекта без наследования.

interface IPaymentStrategy {
    void Pay(decimal amount);
}

class CardPayment : IPaymentStrategy { ... }
class CashPayment : IPaymentStrategy { ... }
class CryptoPayment : IPaymentStrategy { ... }

class Order {
    private IPaymentStrategy _strategy;
    public void SetPayment(IPaymentStrategy s) => _strategy = s;
    public void Checkout(decimal sum) => _strategy.Pay(sum);
}

Где применять: разные способы оплаты, сортировки, валидации, сжатия данных.

Command (Команда)

Инкапсулирует запрос как объект. Позволяет откладывать выполнение, ставить в очередь, поддерживать отмену (undo).

State (Состояние)

Объект меняет своё поведение при изменении внутреннего состояния. Вместо большого switch — отдельные классы состояний.

Iterator (Итератор)

Даёт последовательный доступ к элементам коллекции, не раскрывая её внутреннее устройство.

Паттерны — не серебряная пуля. Если задача решается просто и понятно без паттерна — не тащите паттерн. «Overengineering» (переусложнение) хуже, чем отсутствие паттерна. Паттерн должен упрощать, а не усложнять.

Практические работы

🔧 ПР №1 · Основные шаблоны 40 мин
Задача: реализовать Singleton и Factory Method.

Часть 1. Singleton

Создайте класс AppSettings, который хранит настройки приложения (тема, язык, размер шрифта). Добейтесь, чтобы во всей программе существовал только один экземпляр.

Часть 2. Factory Method

Создайте интерфейс IVehicle с методами Drive() и GetInfo(). Реализуйте Car, Bike, Truck. Создайте фабрику, которая возвращает нужный объект по строке.

🔧 ПР №2 · Порождающие паттерны 45 мин
Задача: реализовать Builder для сложного объекта.

Создайте класс Pizza с полями: размер, сыр, пепперони, грибы, оливки, соус. Реализуйте PizzaBuilder с цепочкой методов:

var pizza = new PizzaBuilder()
    .Size("L")
    .AddCheese()
    .AddPepperoni()
    .AddMushrooms()
    .Build();

Добавьте метод Print(), который выводит состав пиццы.

🔧 ПР №3 · Структурные паттерны 45 мин
Задача: реализовать Decorator для кофе.

Есть базовый интерфейс IBeverage с методами Cost() и Description(). Реализуйте:

  • Espresso — базовый кофе (100 руб.)
  • MilkDecorator — +30 руб.
  • SugarDecorator — +10 руб.
  • CreamDecorator — +40 руб.
  • SyrupDecorator — +50 руб.

Продемонстрируйте: один и тот же кофе с разными комбинациями добавок.

🔧 ПР №4 · Поведенческие паттерны 50 мин
Задача: реализовать Observer и Strategy.

Часть 1. Observer

Создайте класс NewsAgency (Subject). Подписчики: EmailSubscriber, SmsSubscriber, PushSubscriber. При публикации новости все получают уведомление.

Часть 2. Strategy

Создайте систему расчёта скидок:

  • NoDiscount — без скидки
  • PercentDiscount(10) — 10%
  • FixedDiscount(500) — минус 500 руб.
  • SeasonalDiscount — сезонная (например, зимой 15%)

Класс Order принимает стратегию и применяет к сумме.

Вопросы для самопроверки

Вопрос 1. Почему Singleton критикуют?
Три причины:
  • Глобальное состояние. Любой код может изменить Singleton — трудно отследить, кто и когда.
  • Проблемы с тестированием. Нельзя подменить зависимость на mock — Singleton всегда настоящий.
  • Скрытые зависимости. Класс использует Singleton, но это не видно в его конструкторе.
Современная альтернатива: Dependency Injection (DI). Вы регистрируете сервис как «Singletone scope» в контейнере, но получаете его через параметр конструктора — то же поведение, но без глобального состояния.
Вопрос 2. Чем Adapter отличается от Decorator?
Adapter — меняет интерфейс объекта, чтобы его можно было использовать там, где ожидается другой интерфейс. Не добавляет функциональности, только переводит один вызов в другой.

Decorator — добавляет функциональность, сохраняя интерфейс. Оборачивает объект и делает что-то дополнительное.

Пример: Adapter — переходник с USB-C на USB-A. Decorator — чехол для телефона (тот же телефон, но с дополнительной защитой).
Вопрос 3. Почему не стоит использовать паттерны везде?
Паттерн — это усложнение кода ради гибкости. Если гибкость не нужна — усложнение вредит.
  • Класс с одним методом не нуждается в Strategy — достаточно if/else.
  • Объект без изменений не нуждается в Builder — хватит конструктора.
  • Менеджер с одним типом не нуждается в Factory — можно создавать напрямую.
Правило: сначала просто, потом паттерн. Когда код «запахнет» — добавьте паттерн. Не проектируйте «на будущее», которого может не быть.
Вопрос 4. Какой паттерн используется в событийной модели C#?
Observer. Когда вы пишете: 
button.Click += OnButtonClick;
— вы подписываетесь на событие. Кнопка — Subject, ваш метод — Observer. При клике кнопка вызывает Notify(), и все подписчики получают уведомление.

В .NET это реализовано через делегаты и события. В Java — через интерфейс EventListener. В JS — через addEventListener.
