8Тестирование и отладка программного обеспечения

Тестирование — проверка соответствия программы требованиям. Отладка (debugging) — поиск и исправление причин ошибок. Это разные, но связанные задачи: тестирование находит проблемы, отладка устраняет их.

8.1. Зачем тестировать

  • Стоимость ошибки растёт со временем. Баг на этапе разработки — часы. В продакшене — дни, репутация, деньги.
  • Один баг в известном проекте (Ariane 5, 1996) стоил $370 млн из-за неправильного преобразования 64-bit в 16-bit.
  • Тесты = документация. Хорошо написанные тесты показывают, что программа должна делать.
  • Уверенность при рефакторинге. Есть тесты — можно улучшать код, не боясь сломать.
Стоимость исправления бага
ЭтапСтоимость
Требования1×
Проектирование5×
Разработка10×
Тестирование20×
Продакшен100×
Каждый этап увеличивает стоимость исправления в разы.

8.2. Виды тестирования

По уровню (пирамида тестирования)

Пирамида тестирования: много быстрых unit-тестов, меньше интеграционных, ещё меньше E2E.
УровеньЧто тестируетсяСкоростьСколько
Unit (модульное)Отдельная функция или классМилисекундыМного (сотни-тысячи)
Integration (интеграционное)Взаимодействие модулейСекундыСредне (десятки)
E2E (end-to-end)Весь сценарий от UI до БДМинутыМало (единицы-десятки)

По доступу к коду

8.5. Unit-тесты

Unit-тест — тест, проверяющий одну маленькую единицу кода (функцию, метод) в изоляции. Обычно пишется на том же языке, что и код.

Библиотеки для C#

  • xUnit — современный стандарт
  • NUnit — старейшая, гибкая
  • MSTest — от Microsoft
  • Moq — для моков (заглушек)
  • FluentAssertions — читаемые ассерты

Структура теста AAA

  • Arrange — подготовка (создать данные)
  • Act — действие (вызвать метод)
  • Assert — проверка (сравнить результат с ожидаемым)
using Xunit;

public class CalculatorTests {

    [Fact]
    public void Add_TwoPositiveNumbers_ReturnsSum() {
        // Arrange
        var calc = new Calculator();

        // Act
        int result = calc.Add(2, 3);

        // Assert
        Assert.Equal(5, result);
    }

    [Theory]
    [InlineData(0, 0, 0)]
    [InlineData(-1, 1, 0)]
    [InlineData(100, 200, 300)]
    public void Add_VariousInputs_ReturnsCorrectSum(int a, int b, int expected) {
        var calc = new Calculator();
        Assert.Equal(expected, calc.Add(a, b));
    }

    [Fact]
    public void Divide_ByZero_ThrowsException() {
        var calc = new Calculator();
        Assert.Throws<DivideByZeroException>(() => calc.Divide(10, 0));
    }
}

Соглашение об именах

MethodName_Scenario_ExpectedResult

  • Add_TwoPositiveNumbers_ReturnsSum
  • Divide_ByZero_ThrowsException
  • Login_WrongPassword_ReturnsFalse

Моки и стабы

Мок (mock) — поддельный объект, который имитирует поведение реального. Нужен, чтобы протестировать класс в изоляции от БД, сети или внешних сервисов.

// Интерфейс
public interface IEmailService {
    void Send(string to, string subject, string body);
}

// Тестируемый класс
public class UserService {
    private readonly IEmailService _email;
    public UserService(IEmailService email) { _email = email; }

    public void Register(string email) {
        // ... логика регистрации ...
        _email.Send(email, "Добро пожаловать", "...");
    }
}

// Тест с моком
public class UserServiceTests {
    [Fact]
    public void Register_SendsWelcomeEmail() {
        // Arrange
        var emailMock = new Mock<IEmailService>();
        var service = new UserService(emailMock.Object);

        // Act
        service.Register("test@example.com");

        // Assert
        emailMock.Verify(e => e.Send(
            "test@example.com",
            It.IsAny<string>(),
            It.IsAny<string>()
        ), Times.Once);
    }
}

8.6. Покрытие кода (Code Coverage)

Покрытие — процент строк/ветвлений, выполненных при прогоне тестов. Показывает, какие участки кода не протестированы.

ПокрытиеОценка
0-20%Почти не тестируется
20-50%Начальный уровень
50-70%Средний уровень, обычно для бизнес-проектов
70-90%Хорошее покрытие
90-100%Отличное, но иногда избыточное
Правило
Покрытие — не цель, а инструмент. 100% покрытия не гарантирует отсутствия багов. Можно покрыть код, который всегда возвращает true, и не протестировать реальный сценарий. Важно качество тестов, а не цифра.

8.7. Тестирование производительности

ТипЧто проверяет
Load testingСистема под ожидаемой нагрузкой (1000 пользователей)
Stress testingПредел: сколько выдержит, где сломается
Volume testingБольшие объёмы данных (10 ГБ)
Spike testingРезкий рост нагрузки (с 10 до 10 000 за секунду)
Endurance testingРабота в течение долгого времени (24+ часов)

Инструменты: JMeter, k6, LoadRunner, Locust.

8.8. Регрессионное тестирование

Регрессия — ситуация, когда после изменений что-то сломалось в ранее рабочей части. Регрессионные тесты перепроверяют всё, что раньше работало, после каждого релиза.

Автоматизация регрессионных тестов — критична: если после каждого коммита запускать 500 тестов, баги находятся сразу, а не через неделю.

Практические работы

🔧 ПР №1 · Тестирование «белым ящиком» 45 мин
Задача: покрыть unit-тестами класс Calculator.
Класс для тестирования: 
public class Calculator {
    public int Add(int a, int b) => a + b;
    public int Sub(int a, int b) => a - b;
    public int Mul(int a, int b) => a * b;
    public int Div(int a, int b) {
        if (b == 0) throw new DivideByZeroException();
        return a / b;
    }
    public bool IsPrime(int n) {
        if (n < 2) return false;
        for (int i = 2; i * i <= n; i++)
            if (n % i == 0) return false;
        return true;
    }
}

Задания:

  1. Создайте проект тестов (xUnit или NUnit).
  2. Напишите тесты на каждый метод — по 3-4 сценария на метод.
  3. Для Add, Sub, Mul, Div — используйте [Theory] и [InlineData].
  4. Для Div — проверьте выброс исключения при делении на 0.
  5. Для IsPrime — проверьте: 2, 3, 4, 17, 25, отрицательные, 0, 1.
  6. Запустите покрытие кода. Добейтесь 100%.

Вопросы для самопроверки

Вопрос 1. Почему тестов должно быть больше unit, чем E2E?
Три причины:
  1. Скорость. Unit-тест — миллисекунды. E2E — минуты (запуск браузера, БД, сети). 1000 unit-тестов пройдут за секунды, 1000 E2E — за дни.
  2. Стабильность. E2E часто «flaky» — падают из-за сети, задержек, порядка тестов. Unit детерминированы.
  3. Точность диагностики. Если упал unit-тест — сразу видно, где. Если E2E — надо копать, где именно сломалось.
Поэтому пирамида: много unit, меньше интеграционных, совсем мало E2E — только на критичные сценарии.
Вопрос 2. Что такое мок, и зачем он нужен?
Мок — искусственная замена реальной зависимости для тестирования.

Пример: класс UserService использует IEmailService для отправки писем. Реальная отправка — медленная, требует SMTP-сервера, может упасть. В тестах подменяем на мок, который:
  • Не отправляет письма по-настоящему
  • Записывает, что метод был вызван
  • Может вернуть заранее заданный результат
Зачем:
  • Изоляция — тестируем только свой класс
  • Скорость — не ждём реальных операций
  • Контроль — задаём любые сценарии (в т.ч. ошибки)
Вопрос 3. Что означает «flaky test»?
Flaky test («нестабильный тест») — тест, который то проходит, то падает, без изменений в коде. Это худший вид тестов.

Причины:
  • Порядок выполнения. Один тест зависит от другого, а JUnit запускает в случайном порядке.
  • Общее состояние. Тесты делят БД, файлы, статические переменные.
  • Асинхронность. Тест ждёт не того момента (например, 100 мс вместо проверки условия).
  • Дата и время. Тест, зависящий от текущей даты, падает 29 февраля или в полночь.
  • Сеть. Тест зависит от внешнего сервиса — упал сервис, упал тест.
Решение: изолировать тесты, использовать фиксированное время, ждать события, а не секунды, мокать внешние сервисы.
Вопрос 4. В чём разница между отладкой и тестированием?
Тестирование — обнаружение проблем. Вопрос: «Работает ли программа так, как должна?»

Отладка — устранение проблем. Вопрос: «Почему программа работает не так, как должна?»

Порядок такой:
  1. Написали тест — он падает.
  2. Запустили отладчик, нашли причину.
  3. Исправили код.
  4. Тест зелёный.
Отладка без тестов = «угадай, где баг». Тестирование без отладки = «знаю, что не работает, но не знаю почему».
