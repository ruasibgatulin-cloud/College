9Документирование программного обеспечения

Программист пишет код один раз, а читают его много раз — коллеги, тестировщики, он сам через полгода. Хорошая документация экономит недели работы и спасает проекты от провала.

9.1. Зачем документировать

  • Передача знаний. Новый разработчик входит в проект за дни, а не за месяцы.
  • Сопровождение. Через год никто не помнит, почему сделано именно так.
  • Тестирование. QA-инженеры пишут тест-кейсы по спецификации.
  • Юридические требования. Для критичных систем документация обязательна.
  • Помощь пользователю. README и User Guide — лицо проекта.
Мнение индустрии
«Код без документации — это код, который придётся переписывать с нуля». В крупных компаниях документация обязательна в Code Review: PR без обновлённой документации не принимается.

9.2. Виды документации

ТипКому адресованаПримеры
ПользовательскаяКонечным пользователямUser Guide, FAQ, туториалы

9.3. Комментарии в коде

Хорошие комментарии

Отвечают на вопрос «почему», а не «что».

// ХОРОШО — объясняет причину
// Используем бинарный поиск: массив уже отсортирован,
// линейный будет в 1000 раз медленнее на 10⁶ элементов
var index = BinarySearch(arr, value);

// ХОРОШО — предупреждает о подводном камне
// ВНИМАНИЕ: этот API возвращает 200 OK даже при ошибке валидации
// Проверяйте поле result.error дополнительно
var response = await api.Send(data);

// ХОРОШО — ссылка на обсуждение
// См. issue #4213: обход ограничения в библиотеке XYZ
if (value > 1000) { ... }

Плохие комментарии

// ПЛОХО — дублирует код
i++; // увеличить i на 1

// ПЛОХО — устаревший (код изменился, а комментарий нет)
// Возвращает сумму двух чисел
return a * b;

// ПЛОХО — закомментированный код
// var oldValue = CalculateOld();
// var result = oldValue + 5;

// ПЛОХО — бессмысленный
// Это метод обработки
public void Process() { ... }
Правило
Если код настолько непонятен, что требует комментария — сначала попробуйте его переписать. Хорошие имена переменных и функций часто устраняют необходимость в комментариях.

9.4. Docstrings — документация методов

Docstring — специальный комментарий перед классом или методом, описывающий его назначение, параметры и возвращаемое значение. Автоматически собирается в API-документацию.

C# (XML Doc Comments)

/// <summary>
/// Вычисляет сумму двух чисел.
/// </summary>
/// <param name="a">Первое слагаемое.</param>
/// <param name="b">Второе слагаемое.</param>
/// <returns>Сумма a и b.</returns>
/// <exception cref="OverflowException">
/// Если результат превышает int.MaxValue.
/// </exception>
public int Add(int a, int b) {
    return checked(a + b);
}
При наведении на метод в IDE показывается подсказка. Инструменты вроде Sandcastle / DocFX генерируют HTML-документацию.

Python (Google Style)

def calculate_discount(price: float, percent: float) -> float:
    """Рассчитывает цену со скидкой.

    Args:
        price: Исходная цена в рублях.
        percent: Скидка в процентах (0-100).

    Returns:
        Цена после скидки.

    Raises:
        ValueError: Если percent < 0 или > 100.

    Examples:
        >>> calculate_discount(1000, 10)
        900.0
    """
    if not 0 <= percent <= 100:
        raise ValueError("percent must be 0-100")
    return price * (1 - percent / 100)

9.5. README — лицо проекта

README.md — первый файл, который видит человек в репозитории. От него зависит, поймут ли проект или уйдут.

Структура хорошего README

РазделЧто писать
Название + бейджНазвание проекта, статус сборки, версия, лицензия
Краткое описаниеЧто делает проект, для кого (1-2 предложения)
СкриншотыВизуальное представление — обязательно
УстановкаКак развернуть: git clone, зависимости, команды
ИспользованиеПримеры запуска, базовые команды
Стек технологийЯзыки, фреймворки, БД
Структура проектаЧто где лежит
ContributingКак помочь проекту (если open-source)
ЛицензияMIT, Apache 2.0, GPL и т.д.
КонтактыАвтор, email, ссылки
