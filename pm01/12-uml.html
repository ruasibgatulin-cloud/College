12UML и паттерны проектирования

UML (Unified Modeling Language) — унифицированный язык моделирования. Это нотация для описания программных систем: как устроены классы, как они взаимодействуют, какие у системы состояния и процессы. UML — стандарт де-факто в проектировании ПО.

Зачем UML программисту
  • Общий язык. Все понимают одну диаграмму одинаково — не нужно объяснять словами.
  • Проектирование до кода. Легче поправить схему, чем переписать 500 строк.
  • Документация. Остаётся как артефакт — через год напомнит, как всё устроено.
  • Собеседования. На технических интервью часто просят нарисовать диаграмму классов или последовательностей.
  • Командная работа. Архитектор рисует UML, разработчики реализуют по нему код.

12.1. Виды диаграмм UML

Стандарт UML 2.x описывает 14 типов диаграмм, разделённых на две большие группы.

Все 14 диаграмм UML делятся на структурные и поведенческие.

На практике в 90% случаев используются 4 диаграммы:

  • Диаграмма классов — структура системы
  • Диаграмма последовательности — как объекты общаются во времени
  • Диаграмма состояний — жизненный цикл объекта
  • Диаграмма вариантов использования — что система делает для пользователей

Именно на них мы сосредоточимся.

12.2. Диаграмма классов

Class Diagram — основа ООП-проектирования. Показывает классы, их свойства, методы и связи между ними.

Обозначение класса

Класс изображается прямоугольником с тремя секциями: имя, атрибуты, методы.

Модификаторы доступа

СимволМодификаторЗначение
+publicДоступно всем
-privateТолько внутри класса
#protectedКласс и наследники
~packageВнутри пакета
подчёркиваниеstaticОбщий для всех экземпляров
курсивabstractАбстрактный класс / метод

Связи между классами

Самое важное в диаграмме классов — связи. Их шесть основных типов.

Пять основных видов связей: ассоциация, наследование, композиция, агрегация, зависимость.
СвязьОбозначениеСмыслПример
АссоциацияПростая линия«Знает», «использует»Студент учится в Группе
НаследованиеПолый треугольник«Является» (IS-A)Dog IS-A Animal
РеализацияПолый треугольник + пунктирРеализует интерфейсDog implements ISoundable
КомпозицияЗакрашенный ромб«Состоит из», жёсткая связьЧеловек содержит Сердце
АгрегацияПустой ромб«Содержит», слабая связьУниверситет содержит Студентов
ЗависимостьПунктир со стрелкойВременная связьОтчёт использует Printer

Кратность связи (multiplicity)

Показывает, сколько объектов участвует в связи.

ОбозначениеЗначение
1Ровно один
0..1Ноль или один
* или 0..*От нуля до бесконечности
1..*Один или больше
2..5От 2 до 5
Пример: университет
Один Университет содержит 1..* Факультетов.
Один Факультет содержит 1..* Групп.
Одна Группа содержит 1..* Студентов.
Один Студент учится в 1 Группе.

12.3. Диаграмма последовательности

Sequence Diagram — показывает, как объекты обмениваются сообщениями во времени. Читается сверху вниз.

Пользователь вводит URL — браузер шлёт запрос — сервер обрабатывает — отдаёт страницу.

Обозначения

ЭлементЧто значит
Прямоугольник вверхуУчастник (actor, объект, компонент)
Пунктирная вертикальная линияЛиния жизни — существует, пока идёт взаимодействие
Сплошная стрелка →Синхронный вызов (ждём ответ)
Пунктирная стрелка ←Ответ (return)
Прямоугольник на линии жизниАктивный период (что-то делает)
alt (рамка)Альтернативные сценарии (if/else)
loop (рамка)Цикл (повторяющееся действие)
opt (рамка)Опциональный сценарий (если что-то)
par (рамка)Параллельные действия

12.4. Диаграмма состояний

State Diagram — описывает жизненный цикл одного объекта: какие состояния он проходит и как между ними переключается.

Жизненный цикл статьи: Черновик → На проверке → Опубликован (или Отклонён).

Обозначения

ЭлементЗначит
Закрашенный кругНачальное состояние
Круг с точкой внутриКонечное состояние
Скруглённый прямоугольникСостояние (что-то происходит)
СтрелкаПереход (событие, вызывающее смену состояния)
Подпись у стрелки: событие [условие] / действиеПолная форма перехода

Где применяется: жизненный цикл заказа, состояние пользователя (новый / активный / заблокированный), поведение игрового персонажа, состояния конечного автомата.

12.5. Диаграмма вариантов использования

Use Case Diagram — показывает, что система делает для пользователей, без деталей реализации.

Гость может просматривать каталог и зарегистрироваться; пользователь — оформлять заказ (с оплатой).

Обозначения

ЭлементЗначит

ОвалВариант использования (сценарий)
Прямоугольник вокруг оваловГраница системы (что входит, что снаружи)
Сплошная линияАктор участвует в прецеденте

Полый треугольникНаследование между акторами или прецедентами

Пример PlantUML — диаграмма классов из кода

PlantUML рисует диаграмму по тексту. Удобно хранить в Git вместе с кодом.

Практические работы

🎯 ПР №1 · Диаграмма классов — предметная область 50 мин
Задача: построить диаграмму классов для интернет-магазина.

Требования

Интернет-магазин продаёт товары. Есть:

  • Пользователь — имя, email, адрес
  • Товар — название, цена, остаток на складе
  • Категория — название, описание
  • Заказ — дата, статус, сумма
  • Позиция заказа — товар, количество, цена на момент заказа

Что нужно сделать

  1. Нарисуйте диаграмму классов в draw.io.
  2. Для каждого класса — атрибуты и методы с модификаторами (+, -).
  3. Установите связи:
    • Категория → Товар: 1..* (одна категория содержит много товаров)
    • Пользователь → Заказ: 1..*
    • Заказ → Позиция: композиция
    • Позиция → Товар: ассоциация
  4. Укажите кратности связи.
  5. Экспортируйте диаграмму в PNG или SVG.
Сдать: файл диаграммы + PNG/SVG + описание (10 предложений, что и почему так связано).
🎯 ПР №2 · Диаграмма последовательности 40 мин
Задача: описать процесс «Оформление заказа в интернет-магазине».

Участники

  • Покупатель
  • Веб-интерфейс (браузер)
  • Backend (сервер магазина)
  • Платёжный шлюз
  • База данных

Сценарий

  1. Покупатель нажимает «Оформить заказ».
  2. Веб отправляет запрос на backend.
  3. Backend проверяет наличие товара в БД.
  4. Если всё в наличии — backend обращается к платёжному шлюзу.
  5. Шлюз возвращает статус оплаты.
  6. При успехе backend сохраняет заказ в БД.
  7. Покупателю показывается страница «Спасибо за заказ».

Что нужно сделать

  1. Нарисуйте диаграмму последовательности (draw.io или PlantUML).
  2. Используйте рамку alt для сценария «оплата не прошла».
  3. Используйте loop для проверки каждого товара в заказе.
Сдать: диаграмма + пояснение.
🎯 ПР №3 · Диаграмма состояний 40 мин
Задача: описать жизненный цикл заказа в интернет-магазине.

Требования

Заказ может находиться в состояниях:

  • Создан — пользователь оформил
  • Оплачен — платёж прошёл
  • Собирается — на складе комплектуют
  • Отправлен — передан курьеру
  • Доставлен — получен покупателем
  • Отменён — пользователь или система отменили

Что нужно сделать

  1. Нарисуйте диаграмму состояний.
  2. Подпишите стрелки событиями: «Оплата», «Отмена клиентом», «Передача курьеру» и т.д.
  3. Укажите начальное и конечное состояния.
  4. Добавьте одно условие (например, «Отмена возможна только до состояния Собирается»).
Сдать: диаграмма + пояснение.
🎯 ПР №4 · Диаграмма вариантов использования 40 мин
Задача: описать функционал системы «Библиотека».

Акторы

  • Читатель — ищет книги, берёт, возвращает
  • Библиотекарь — выдаёт, принимает, управляет каталогом
  • Администратор — управляет пользователями и настройками

Прецеденты (минимум 6)

  • Поиск книги по названию / автору
  • Просмотр карточки книги
  • Взять книгу
  • Вернуть книгу
  • Добавить книгу в каталог
  • Удалить книгу из каталога
  • Заблокировать читателя

Что нужно сделать

  1. Нарисуйте диаграмму вариантов использования.
  2. Обозначьте границу системы.
  3. Используйте «include» для обязательных шагов (например, «Взять книгу» включает «Проверить наличие»).
  4. Используйте «extend» для опциональных (например, «Продлить срок» расширяет «Взять книгу»).

Выберите одну область

  • Онлайн-кинотеатр
  • Система управления задачами (типа Trello)
  • Блог-платформа

Что нужно сдать

  1. Диаграмма вариантов использования — что система делает
  2. Диаграмма классов — модели и связи (минимум 6 классов)
  3. Диаграмма последовательности — один ключевой сценарий
  4. Диаграмма состояний — жизненный цикл главной сущности
  5. Описание проекта (1-2 страницы):
    • Что за система, для кого
    • Основные сущности и их связи
    • Обоснование архитектурных решений
Критерии оценки
  • Отлично — все 4 диаграммы корректны, связи правильные, есть описание и обоснование.
  • Хорошо — диаграммы в целом верные, но есть мелкие ошибки в связях или кратности.
  • Удовлетворительно — есть все 4 диаграммы, но с заметными ошибками.
  • Неудовлетворительно — не все диаграммы или они некорректны.

Вопросы для самопроверки

Вопрос 1. Чем UML отличается от языка программирования?
UML — это нотация, а не язык для исполнения.

  • UML описывает, что и как устроено — словами, символами, диаграммами.
  • Язык программирования — исполняется компьютером.
Из UML-диаграммы нельзя запустить программу. Она — для понимания, обсуждения, документирования. Некоторые инструменты генерируют код по диаграммам (round-trip engineering), но это ограниченные возможности.

Аналогия: чертёж дома — это UML, а сам дом — это код. По чертежу можно построить, но жить в нём нельзя.
Вопрос 2. Чем композиция отличается от агрегации?
Главное — жизненный цикл частей.

Композиция (закрашенный ромб):
  • Часть не может существовать без целого.
  • Удалили целое — удалились части.
  • Пример: Заказ → Позиция заказа. Удалили заказ — позиции больше не нужны.
Агрегация (пустой ромб):
  • Часть может существовать отдельно от целого.
  • Удалили целое — части остаются.
  • Пример: Университет → Студент. Университет закрыли, студенты не исчезли.
Вопрос 3. Когда использовать диаграмму последовательности, а когда — состояний?
Они отвечают на разные вопросы:

Последовательность (Sequence): «Как несколько объектов общаются во времени, чтобы решить задачу?»
Используется, когда важно показать сценарий взаимодействия: например, «пользователь вводит URL — браузер шлёт запрос — сервер отвечает».

Состояния (State): «Какие стадии проходит один объект за свою жизнь?»
Используется, когда важно показать жизненный цикл сущности: заказ → оплачен → отправлен → доставлен.

Обе диаграммы часто применяются вместе: одна показывает систему «снаружи», другая — «изнутри».
Вопрос 4. Обязательно ли рисовать UML-диаграммы в проекте?
Формально — нет, но на практике очень полезно.

Когда UML обязателен:
  • Проект делают 3+ разработчика — нужна общая схема.
  • Сложная предметная область (финансы, медицина, банки).
  • Проект развивается годами — нужна документация для новых разработчиков.
  • Заказчик требует проектной документации.
Когда можно опустить:
  • Маленький pet-проект.
  • Прототип или MVP.
  • Задача тривиальная.
Реальность: многие команды рисуют минимально — только диаграмму классов верхнего уровня и 1-2 диаграммы последовательности для ключевых сценариев. Полные 14 диаграмм никто не делает.
