2Структурное программирование

Структурное программирование (СП) — парадигма, появившаяся в 1960-70-х как ответ на «спагетти-код». Идея проста: любую программу можно построить из трёх базовых конструкций. Никаких goto и прыжков по всему коду.

2.2. Почему отказались от goto

До СП программисты свободно использовали оператор goto — «перейти к метке». Это порождало спагетти-код: программу, в которой поток управления прыгает по десяткам меток, и понять логику невозможно.

Статья Эдсгера Дейкстры 1968 года «О вреде оператора goto» стала манифестом структурного программирования. Доказано: любой алгоритм можно записать без goto, используя только три базовые конструкции.

// Плохо: спагетти с goto
start:
  if (x < 0) goto error;
  if (y == 0) goto skip;
  x = x / y;
skip:
  if (x > 100) goto done;
  x = x * 2;
  goto start;
error:
  printf("Error");
done:
  return x;
Такой код сложно читать, тестировать и поддерживать. В современном коде goto почти не используется.

2.3. Разбиение на модули и функции

Второй принцип СП — декомпозиция: большая задача разбивается на маленькие функции. Каждая функция решает одну задачу.

Правила хорошей функции:

  • Делает одно дело, и делает его хорошо
  • Помещается на один экран (~20-30 строк)
  • Понятное имя (calculateTotal, validateEmail)
  • Минимум параметров (идеально — 0-3)
  • Не имеет «побочных эффектов» без необходимости
Пример декомпозиции
Плохо — одна большая функция: 
function processOrder(order) {
  // проверка заказа
  if (!order.items) return null;
  if (order.items.length === 0) return null;
  // расчёт суммы
  let total = 0;
  for (let i of order.items) total += i.price * i.qty;
  // скидка
  if (total > 1000) total *= 0.9;
  // отправка email
  sendEmail(order.user, `Заказ на ${total} руб.`);
  // сохранение в БД
  saveToDb(order, total);
  return total;
}
Хорошо — разбито на функции: 
function processOrder(order) {
  if (!isValidOrder(order)) return null;
  const total = calculateTotal(order.items);
  const discounted = applyDiscount(total);
  sendOrderEmail(order.user, discounted);
  saveOrder(order, discounted);
  return discounted;
}

2.4. Оценка сложности алгоритмов (Big O)

Big O — оценка того, как время работы алгоритма растёт с увеличением входных данных. Обозначается $O(f(n))$, где $n$ — размер входа.

ОбозначениеНазваниеПримерn = 1000n = 10⁶
$O(1)$КонстантнаяДоступ к массиву по индексу11
$O(\log n)$ЛогарифмическаяБинарный поиск1020
$O(n)$ЛинейнаяПроход по массиву1 00010⁶
$O(n \log n)$ЛинеарифмическаяБыстрая сортировка10 0002·10⁷
$O(n^2)$КвадратичнаяПузырьковая сортировка, двойной цикл10⁶10¹²
$O(2^n)$ЭкспоненциальнаяПеребор подмножествДаже n=50 — вечность
Рост времени работы алгоритмов с увеличением n.
Правило
Разница между $O(n^2)$ и $O(n \log n)$ — это разница между «программа работает за 30 секунд» и «программа работает за 3 дня». При миллионе элементов лучше отсортировать слиянием, чем пузырьком.

Пример: три способа найти число в массиве

// O(n) — линейный поиск
for (let i = 0; i < arr.length; i++) if (arr[i] === x) return i;

// O(log n) — бинарный поиск (массив отсортирован)
let lo = 0, hi = arr.length - 1;
while (lo <= hi) {
  const mid = Math.floor((lo + hi) / 2);
  if (arr[mid] === x) return mid;
  if (arr[mid] < x) lo = mid + 1; else hi = mid - 1;
}

// O(1) — хеш-таблица (Set / Map)
const set = new Set(arr);
return set.has(x);
Три подхода — разная сложность. Выбор зависит от задачи.

2.5. Неразрешимые задачи

Есть задачи, для которых невозможно написать алгоритм, работающий за конечное время:

  • Проблема остановки (Алан Тьюринг, 1936): по описанию программы и её входным данным определить, завершится ли она когда-нибудь.
  • Проблема эквивалентности: определить, делают ли две программы одно и то же.
  • Десятая проблема Гильберта: определить, имеет ли диофантово уравнение решение в целых числах.

Эти задачи алгоритмически неразрешимы: доказано, что алгоритма не существует. Иногда можно решить частный случай — но общего решения нет.

Задача: оценить сложность алгоритмов сортировки.

Часть 1. Пузырьковая сортировка — O(n²)

function bubbleSort(arr) {
  for (let i = 0; i < arr.length - 1; i++) {
    for (let j = 0; j < arr.length - i - 1; j++) {
      if (arr[j] > arr[j + 1]) {
        [arr[j], arr[j + 1]] = [arr[j + 1], arr[j]];
      }
    }
  }
  return arr;
}

Объясните: почему два вложенных цикла дают $O(n^2)$?

Часть 2. Сортировка слиянием — O(n log n)

Массив делится пополам, каждая половина сортируется, потом сливается. Уровней деления: $\log_2 n$. На каждом уровне — проход по n элементам.

Задача: понять сложность разных типов алгоритмов.

Рекурсивные алгоритмы

Числа Фибоначчи через наивную рекурсию — $O(2^n)$:

function fib(n) {
  if (n <= 1) return n;
  return fib(n - 1) + fib(n - 2);
}

// С мемоизацией — O(n)
const memo = {};
function fibMemo(n) {
  if (n <= 1) return n;
  if (memo[n]) return memo[n];
  return memo[n] = fibMemo(n - 1) + fibMemo(n - 2);
}

Проверьте: посчитайте время работы обоих вариантов для n = 35.

Эвристические алгоритмы

Не гарантируют точный ответ, но быстро находят «хорошее» решение. Пример — задача коммивояжёра (TSP): точное решение требует $O(n!)$, эвристики (муравьиный алгоритм, метод ближайшего соседа) дают результат за $O(n^2)$.

Вопросы для самопроверки

Вопрос 1. Почему $O(n \log n)$ лучше $O(n^2)$?
Разница видна на больших $n$:
  • При $n = 1000$: $n^2 = 10^6$, $n\log n \approx 10^4$ — разница в 100 раз
  • При $n = 10^6$: $n^2 = 10^{12}$, $n\log n \approx 2\cdot 10^7$ — разница в 50 000 раз
В секундах: $O(n^2)$ при $n=10^6$ — несколько часов. $O(n\log n)$ — меньше секунды.
Вопрос 2. Что означает «асимптотическая сложность»?
Это оценка поведения алгоритма при стремлении размера входа к бесконечности. Константы и младшие члены отбрасываются — они неважны на больших $n$.

Например, алгоритм, работающий за $2n^2 + 100n + 500$, имеет сложность $O(n^2)$: при больших $n$ главный член — $n^2$, остальное — шум.

Асимптотика не говорит, сколько алгоритм работает сейчас — она говорит, как он будет работать, если данных станет в 10 раз больше.
Вопрос 3. Может ли алгоритм быть O(1), но работать медленнее, чем O(n)?
Да, на маленьких данных. Асимптотика описывает поведение при росте $n$, а не абсолютное время.

Пример: поиск в хеш-таблице $O(1)$, но нужно сначала построить таблицу — это $O(n)$. Если ищем один раз — линейный поиск быстрее. Если ищем 1000 раз — таблица выиграет.

Это называется «асимптотический разрыв» и учитывается при оптимизации.
Вопрос 4. Почему проблему остановки нельзя решить?
Доказательство от противного: предположим, существует программа Halt(P, x), которая говорит, завершится ли программа P на входе x. Построим программу Loop(P): «если Halt(P, P) вернёт “завершится” — то зациклиться; иначе — завершиться».

Теперь спросим: завершится ли Loop(Loop)?
— Если завершится, значит Halt(Loop, Loop) сказал «зациклится» — противоречие.
— Если зациклится, значит Halt сказал «завершится» — тоже противоречие.

Единственный выход — Halt не существует. Это доказал Алан Тьюринг в 1936 году.
