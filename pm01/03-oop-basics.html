3Объектно-ориентированное программирование

ООП — парадигма, в которой программа строится из объектов, взаимодействующих друг с другом. Каждый объект — экземпляр класса, обладающий состоянием (данными) и поведением (методами).

3.1. Класс и объект

ПонятиеЧто этоПример
КлассШаблон, «чертёж» для создания объектовclass Student
ОбъектКонкретный экземпляр классаСтудент Иванов
ПолеПеременная внутри класса (состояние)string Name

Класс Student — чертёж, объекты ivan и petrov — конкретные экземпляры.

3.2. Четыре принципа ООП

1. Инкапсуляция

Данные и методы, работающие с ними, находятся в одном классе. Доступ к внутреннему состоянию — только через публичный интерфейс.

Пример на C#
public class BankAccount {
    private decimal balance;  // скрыто от внешнего мира

    public void Deposit(decimal amount) {
        if (amount <= 0) throw new ArgumentException();
        balance += amount;
    }

    public decimal GetBalance() => balance;  // публичный доступ
}
Внешний код не может напрямую изменить balance — только через Deposit, где есть валидация. Это защищает от случайных ошибок.

2. Наследование

Класс-потомок получает поля и методы родителя. Позволяет переиспользовать код и строить иерархии.

Dog и Cat наследуют от Animal, но переопределяют Sound().

3. Полиморфизм

Один и тот же метод может вести себя по-разному у разных классов. Позволяет работать с объектами через общий интерфейс.

Animal[] zoo = { new Dog(), new Cat(), new Cow() };
foreach (var animal in zoo) {
    Console.WriteLine(animal.Sound());  // Woof, Meow, Moo
}
Один вызов Sound() — разное поведение в зависимости от реального типа объекта.

4. Абстракция

Работаем с сущностью на уровне «что она делает», скрывая «как именно». Абстрактный класс или интерфейс описывает контракт, а детали реализации — в потомках.

abstract class Shape {
    public abstract double Area();
    public abstract double Perimeter();
}

class Circle : Shape {
    public double Radius { get; set; }
    public override double Area() => Math.PI * Radius * Radius;
    public override double Perimeter() => 2 * Math.PI * Radius;
}

Правило
Поля делайте private, доступ — через свойства (get/set) или методы. Это основа инкапсуляции. Исключение — константы и readonly.

3.4. Принципы SOLID

Пять принципов проектирования классов, сформулированные Робертом Мартином (Uncle Bob). Помогают делать код гибким и поддерживаемым.

S — Single Responsibility (Единственная ответственность)

Класс должен иметь одну причину для изменения. Если класс занимается и логикой, и сохранением в БД, и отправкой email — это три ответственности, надо разделить.

O — Open/Closed (Открыт для расширения, закрыт для изменения)

Можно добавлять новое поведение, не меняя существующий код. Достигается через наследование, интерфейсы, композицию.

L — Liskov Substitution (Подстановка Барбары Лисков)

Объект подкласса должен заменять объект родителя без сюрпризов. Если Bird умеет Fly(), то Penguin : Bird не должен ломать код, ожидающий, что птица летает.

I — Interface Segregation (Разделение интерфейсов)

Много маленьких интерфейсов лучше одного большого. Класс не должен реализовывать методы, которые ему не нужны.

D — Dependency Inversion (Инверсия зависимостей)

Зависим от абстракций, а не от конкретных классов. Вместо new MySQLDatabase() — параметр типа IDatabase. Легко менять реализацию и тестировать.

Пример SOLID на практике
Плохо: 
class Order {
    public void SaveToDb() { ... }
    public void SendEmail() { ... }
    public decimal CalculateTotal() { ... }
}
Хорошо (разделение ответственности): 
class Order { decimal Total; List<Item> Items; }
class OrderRepository { void Save(Order o) { ... } }
class EmailService { void SendReceipt(Order o) { ... } }
class OrderCalculator { decimal Calculate(Order o) { ... } }

Вопросы для самопроверки

Вопрос 1. Что такое «инкапсуляция» простыми словами?
Инкапсуляция — это сокрытие внутренней реализации объекта и предоставление доступа только через понятный интерфейс.

Аналогия: банкомат. Вы вставляете карту, вводите PIN, получаете деньги. Вы не знаете, как внутри устроены счётчики купюр, какая база данных, как считаются деньги. Это инкапсуляция: сложность скрыта, снаружи — простой интерфейс.

В коде: поля класса private, доступ — через публичные методы с валидацией.
Вопрос 2. Что общего у полиморфизма и наследования?
Они работают в паре: наследование создаёт иерархию, а полиморфизм позволяет использовать эту иерархию единообразно.

Наследование: Dog — это Animal, он получает все его методы.
Полиморфизм: если у Animal есть метод Sound(), и Dog его переопределяет — то вызов animal.Sound() для объекта Dog даст «Woof», а для Cat — «Meow».

Без наследования полиморфизм тоже возможен — через интерфейсы. Классы могут не иметь общего предка, но реализовывать общий интерфейс.
Вопрос 3. Что нарушает принцип Лисков?
Классический пример — квадрат и прямоугольник.

Rectangle имеет методы SetWidth(w) и SetHeight(h), независимые друг от друга. Square наследует, но у него стороны равны — при SetWidth(5) должна меняться и высота. Это ломает контракт: код, работающий с прямоугольником, ожидает, что высота останется прежней.

Другой пример: класс Bird с методом Fly(). Penguin : Bird — не умеет летать. Если метод Fly() возвращает исключение — код, использующий Bird, ломается.

Решение: не делать Penguin наследником Bird с Fly(). Разделить на Bird и FlyingBird.
Вопрос 4. Зачем нужны интерфейсы, если есть абстрактные классы?
Разные цели:
  • Абстрактный класс — когда есть общая реализация, которую хочется переиспользовать. Наследник получает и код, и контракт.
  • Интерфейс — когда нужен только контракт. Любой класс может реализовать интерфейс, независимо от иерархии.
Ключевое отличие: класс может реализовать много интерфейсов, но наследоваться только от одного класса (в C#, Java).

Пример: Dog может реализовать IWalkable, ISwimmable, IFeedable — три независимых контракта. А унаследоваться — только от Animal.
