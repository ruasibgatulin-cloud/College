6Оптимизация и рефакторинг кода

Программисты пишут код не для компьютера, а для других программистов — включая себя через полгода. Рефакторинг и оптимизация — два инструмента, которые делают код понятным и быстрым.

6.1. Что такое рефакторинг

Рефакторинг — изменение структуры кода без изменения поведения. После рефакторинга программа работает так же, но код становится чище.

Метафора
Рефакторинг — это уборка в комнате. Вещи те же, но найти нужное легко. Если через полгода открыть код и не понимать, что там — пора рефакторить.

6.3. Техники рефакторинга

1. Extract Method (извлечь метод)

Длинный код разбиваем на методы с понятными именами.

// БЫЛО
void PrintInvoice(Order order) {
    Console.WriteLine("Счёт №" + order.Id);
    Console.WriteLine("Дата: " + order.Date);
    decimal total = 0;
    foreach (var item in order.Items) total += item.Price * item.Quantity;
    Console.WriteLine("Итого: " + total);
}

// СТАЛО
void PrintInvoice(Order order) {
    PrintHeader(order);
    PrintTotal(order);
}
void PrintHeader(Order order) { ... }
void PrintTotal(Order order) { ... }

2. Rename (переименовать)

Понятные имена — половина читаемости.

ПлохоХорошо
ddaysUntilDeadline
calc()calculateTotalPrice()
flagisEmailVerified
tempuserInput
x1, x2, x3width, height, depth

3. Guard Clauses (ранний выход)

Вместо вложенных условий — проверки в начале и ранние return.

// БЫЛО
decimal GetDiscount(User user) {
    if (user != null) {
        if (user.IsActive) {
            if (user.OrdersCount > 10) {
                return 0.15m;
            } else {
                return 0.05m;
            }
        } else {
            return 0m;
        }
    }
    return 0m;
}

// СТАЛО
decimal GetDiscount(User user) {
    if (user == null) return 0m;
    if (!user.IsActive) return 0m;
    if (user.OrdersCount > 10) return 0.15m;
    return 0.05m;
}

4. Replace Magic Number with Constant (замена магического числа)

// БЫЛО
if (order.Total > 10000) discount = 0.1m;

// СТАЛО
private const decimal VIP_THRESHOLD = 10000m;
private const decimal VIP_DISCOUNT = 0.1m;

if (order.Total > VIP_THRESHOLD) discount = VIP_DISCOUNT;

5. Удаление дубликатов (DRY — Don't Repeat Yourself)

// БЫЛО — три похожих метода
void SaveUserToFile(User u) { /* ... 20 строк ... */ }
void SaveOrderToFile(Order o) { /* ... 20 строк ... */ }
void SaveProductToFile(Product p) { /* ... 20 строк ... */ }

// СТАЛО — обобщённый метод
void SaveToFile<T>(T entity, string path) {
    var json = JsonSerializer.Serialize(entity);
    File.WriteAllText(path, json);
}

6.5. Оптимизация производительности

Оптимизация — это не «сделать код короче», а ускорить работу. Правило: не оптимизируйте преждевременно.

Правило Кнута
«Преждевременная оптимизация — корень всех зол». Сначала измерьте, где узкое место (профилирование), и оптимизируйте только его. 90% времени программа проводит в 10% кода.

Основные техники

ПроблемаЧто делать
Много итераций поиска в массивеЗаменить массив на HashSet/Dictionary (O(n) → O(1))
Часто вызывается тяжёлая функция с одинаковыми аргументамиКэширование (мемоизация)
Много строковых конкатенаций в циклеStringBuilder вместо + (O(n²) → O(n))
Постоянные обращения к БД в циклеBatch-запрос (один SELECT вместо 1000)
Много лишних выделений памятиПереиспользовать объекты (пул), избегать аллокаций в горячих циклах
Ожидание I/O блокирует CPUАсинхронность (async/await)

Пример: StringBuilder vs конкатенация

// ПЛОХО: O(n²)
string result = "";
for (int i = 0; i < 10000; i++) {
    result += i.ToString() + ",";
}

// ХОРОШО: O(n)
var sb = new StringBuilder();
for (int i = 0; i < 10000; i++) {
    sb.Append(i).Append(",");
}
string result = sb.ToString();
Каждое += создаёт новую строку. Для 10 000 итераций — миллионы операций. StringBuilder добавляет в буфер.

Пример: Dictionary вместо List для поиска

// ПЛОХО: O(n) на каждый поиск
var users = new List<User>();
User FindById(int id) {
    foreach (var u in users) if (u.Id == id) return u;
    return null;
}

// ХОРОШО: O(1) на каждый поиск
var usersById = new Dictionary<int, User>();
User FindById(int id) => usersById.TryGetValue(id, out var u) ? u : null;
Для 10 000 пользователей и 10 000 запросов: список — 100 миллионов операций, словарь — 10 000.

Вопросы для самопроверки

Вопрос 1. Чем рефакторинг отличается от оптимизации?
Рефакторинг — улучшение структуры кода без изменения поведения. Результат: код понятнее, легче поддерживать.

Оптимизация — улучшение производительности. Результат: код работает быстрее или использует меньше памяти.

Иногда их путают: «оптимизировать код» часто означает «причесать, почистить». Но с точки зрения профессионала — это разные задачи. Рефакторинг делают всегда, оптимизацию — только когда нужно.
Вопрос 2. Почему нельзя рефакторить без тестов?
Рефакторинг по определению не меняет поведение. Но как проверить, что вы не сломали ничего? Только тестами. Если после рефакторинга все тесты зелёные — поведение сохранено.

Без тестов рефакторинг превращается в «переписывание кода с надеждой, что работает». Ошибки обнаруживаются на продакшене — через дни или недели.

Правило: сначала покрой тестами, потом рефакторь. Это как страховка.
Вопрос 3. Что означает принцип DRY?
DRY = Don't Repeat Yourself («не повторяйся»). Каждое знание в системе должно иметь единственное представление.

Плохо: формула расчёта НДС скопирована в 5 местах. Если ставка изменится — надо править 5 файлов, можно забыть один.

Хорошо: одна функция CalculateVAT(), вызывается из всех мест. Меняем в одном — работает везде.

Но: DRY не означает «избегай любого повтора». Иногда два похожих куска кода — это случайное совпадение, и объединять их не стоит. Главное — избегать повтора логики, а не букв.
Вопрос 4. Когда НЕ нужно оптимизировать?
  • Когда код работает достаточно быстро. Если программа отвечает за 50 мс — незачем тратить недели на 10 мс.
  • Когда оптимизация усложняет код. Если ради +20% скорости код станет нечитаемым — не стоит.
  • Когда неясно, где узкое место. Оптимизация «на глаз» часто мимо цели. Сначала — профилирование.
  • На раннем этапе. Преждевременная оптимизация — зло. Сначала рабочая версия, потом замеры, потом улучшения.
Правило: measure, don't guess («измеряй, а не гадай»).
